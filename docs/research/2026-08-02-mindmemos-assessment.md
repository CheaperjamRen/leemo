# MindMemOS 对 Leemo 的价值评估（2026-08-02）

## 结论先行

MindMemOS 的研究价值高，但**当前不接入 Leemo MVP**。它最值得借鉴的是“记忆可演化、可反馈、可跨 Agent 复用”的方向，不是现阶段的部署形态。

Leemo 已有 Auto Memory + 治理账本，解决的是用户可见的事实、偏好、时间、来源、替代和撤销。MindMemOS 若未来接入，只能作为可删除、可重建的语义检索/关系索引，不能成为记忆真源，更不能绕过用户的编辑、遗忘与撤销。

## 为什么现在不接

- 官方本地快速启动会拉起 FastAPI，并依赖 Qdrant、Neo4j、Kafka；可观测性组合还包括 ClickHouse、OpenTelemetry 与 Grafana。对近零预算、单机桌面 MVP 来说，安装体积、启动进程、内存和故障面都不合算。
- 记忆抽取与演化至少需要聊天、Embedding，另可配置 rerank 模型，会引入持续费用与后台偷跑心智；这与 Leemo 当前“本地优先、成本可见、默认不偷跑”的要求冲突。
- README 把 Lite mode、文件系统记忆和更多 Agent 集成列在 Coming Features，说明最适合 Leemo 的轻量嵌入形态尚未交付。
- 项目在 2026-06-30 才正式发布，仍处早期。README 声明 MIT，但仓库根目录当前没有可核验的 LICENSE 文件，GitHub 也未识别许可证；在许可证文件补齐前，不复制源码进入产品。
- 当前没有来自 5-10 名真实用户的证据表明 Leemo 的主要问题是“召回算法不够强”，而不是记忆写入质量、错误事实治理、时间更新或用户缺少纠正入口。

## 值得吸收的产品思想

1. **反馈闭环**：用户纠正一次后，不只改展示，还应成为检索与写入策略的负反馈证据。
2. **跨 Agent 可移植**：未来多 Agent 各自上下文隔离，但共享同一受治理的用户/本子记忆视图。
3. **经验与 Skill 相连**：反复成功或失败的任务可以形成 Skill 候选，但必须由用户或开发者确认后再固化，不能后台自动改写已安装 Skill。
4. **离线整理不等于静默删除**：聚合、降权和建立关系可以后台做；事实状态、替代链和删除仍由 Leemo 账本决定。

## 未来正确接法

```text
用户对话 / 文件 / momo 工具结果
              |
              v
Leemo 受治理记忆账本（唯一真源，可看、可改、可撤销）
              |
              v
可重建事件流 / 脱敏导出
              |
              v
MindMemOS 或其他语义索引（可选插件，可整库删除重建）
              |
              v
召回候选 -> Leemo 权限、范围、时间和状态过滤 -> 注入 momo
```

必须满足：

- 全局、本子、默认工作区严格隔离；本子记忆不串线。
- 已删除、已替代、待确认记忆不能被索引层“复活”。
- 索引不可直接写用户画像；推断先进入 Leemo 候选态。
- 默认不开云服务，不上传真实用户资料；成本、频率和最后运行时间可见。
- 索引停机或损坏时，Leemo 对话、记忆编辑和普通召回仍可工作。

## 何时重新评估

先让 5-10 名内测用户连续使用一到两周。只有出现可复现的真实失败，例如“用户明明纠正过却持续召回旧值”“跨周任务找不到相关背景”“本子资料关系检索明显不足”，才做一张隔离 PoC 卡：

1. 只用合成数据；
2. 不改当前账本；
3. 对比现有 SQLite/关键词召回与 MindMemOS 的命中率、错误召回、延迟、内存和成本；
4. 达到明确收益后再决定是否集成。
