# Leemo 窗口可用性底线与窄窗工作台验收

## 结论

Leemo 主窗口最小外框定为 `800×640`。窗口宽度低于 `1024px` 时，文件预览不再与对话列并排挤压，而是成为侧栏右侧的单主界面页面；关闭预览后，原对话与输入区原位恢复。

这不是把桌面应用锁成大窗口。`800px` 仍允许常见的并排工作，同时给固定侧栏、主输入区和文件操作保留可用宽度。旧的 `720px` 只保留为额外压力测试，不再代表用户可实际拖到的产品下限。

## 已安装竞品只读证据

2026-08-03 对本机已安装包的主进程代码做只读检查，没有启动模型任务或修改竞品文件：

| 产品 | 本机版本 | 主窗口最小尺寸 | 观察 |
|---|---:|---:|---|
| NewMax | 1.1.5 | `480×460` | 默认窗口为 `1440×900`；本卡未目验其 renderer 在窄窗下的可用性 |
| WorkBuddy | 5.3.5 | `800×600` | 还监听显示器工作区变化，动态修正有效下限和窗口边界 |
| Kimi | 3.1.6 | `400×600` | 主壳与部分工作窗使用该下限；本卡未目验其 renderer 在窄窗下的可用性 |

竞品没有统一答案。Leemo 当前工作台同时承载本子侧栏、对话、输入区和原生文件预览，直接采用 `400px` 或 `480px` 会让主任务区失去可用意义；采用 `1024px` 又会显著损害用户与资料、浏览器或编辑器并排工作的场景。因此选择与 WorkBuddy 接近的 `800px`，并在布局层明确切换，而不是只设一个数字。

## 实现边界

- Electron `BrowserWindow`：`minWidth: 800`、`minHeight: 640`。
- `>=1024px`：对话与预览保持并排。
- `<1024px`：预览绝对定位到主内容区，宽度占满侧栏右侧；底层对话列不重排、不缩窄。
- 文件树仍为临时抽屉，点击文件后自动收起。
- 侧栏不会因为缩窗被静默折叠，避免用户失去位置感。

## 打包应用用户路径

验收脚本 `scripts/verify-window-usability-floor.mjs` 启动隔离的 `Leemo.exe`，先使用 Windows 原生 `SetWindowPos` 将外框设为 `1040×720`，证明宽窗仍是对话与预览并排；再请求缩到 `640×480`，以 `GetWindowRect` 确认 Electron 将其约束在 `800×640`。渲染层全程走可见控件：

1. 切到工作台，在 `1040×720` 打开文件树并点击真实工作区中的 `窄窗.md`；
2. 确认宽窗预览与对话并排，二者边缘衔接，底层对话仍可交互；
3. 关闭预览，缩到原生下限 `800×640`，记录对话与输入区基线；
4. 再次打开同一文件，确认预览成为完整单主界面、页面横向溢出为 0；
5. 确认预览接管焦点，底层对话同时获得 `inert` 与 `aria-hidden`，不会被键盘误操作或读屏重复读取；
6. 预览保持打开时从文件树切换到第二份真实 Markdown，确认活动文件变化后焦点仍回到预览；再逐个关闭标签，确认输入区以同一几何位置完整恢复并重新获得焦点。

本机 175% 缩放下，请求 `640×480` 后 Windows 外框回读为精确 `800×640`，renderer CSS 视口为 `787×578`；预览和输入区宽度均为约 `607px`。DPI 取整产生约 `0.43 CSS px` 的边缘差，验收只容忍 `1px`，仍会抓住真实裁切。

证据：`docs/research/audit-shots/window-floor-facts.json`、`window-floor-side-by-side-1040x720.png`、`window-floor-preview-800x640.png` 与 `window-floor-restored-800x640.png`。6 项判据同时覆盖原生外框、宽窗并排、窄窗四边几何、交互隔离、文件切换焦点和输入区恢复，不把“元素仍在 DOM 中”误判为用户可用。

## 尚未外推

- 本卡只证明 Windows x64 当前安装包路径，不代表 macOS/Linux 已做同等窗口验收。
- `720px` 浏览器 fixture 仍可发现更激进的响应式问题，但不等同于 Electron 原生窗口能力。
- 本卡不重做整体视觉系统；侧栏、输入框、AskUserCard 等视觉打磨仍属于后续统一视觉里程碑。
