# Leemo 本轮开发流程复盘：从“局部修好”到“整体验收”

日期：2026-08-11

范围：本轮 Leemo 产品设计、视觉重构、真实交互接线、视觉验收与 subagent 编排

性质：过程复盘与后续强制工作协议；不是产品完成证明，也不替代现有验收台账

## 0. 结论先行

本轮最大的失败不是“某个按钮做丑了”，而是**反复用局部正确代替整体正确**：

- 用测试通过代替真实用户路径通过；
- 用组件存在代替组件可用；
- 用某个控件被删掉代替删掉后父布局仍均衡；
- 用无溢出、无遮挡代替界面好看、紧凑、有层次；
- 用少量空 fixture 截图代替真实数据规模下的产品状态；
- 用“已经参考竞品”代替对竞品几何、密度、状态和动效的逐项拆解；
- 用独立审计给出的分数代替主开发者亲自发现并关闭问题。

用户最新指出的“新建对话按钮只占半截、右侧留下大片无意义空白”是这个失误的标准样本：重复折叠按钮虽然被移除，但验收只确认“重复按钮不见了”，没有检查**原父容器重新排版后，主操作是否占据合理宽度、视觉重心是否仍平衡、空白是否有意义**。

因此，后续不再以“组件级完成”作为默认粒度。视觉任务的最小完成单元必须是：

> **组件状态完整 + 父布局成立 + 整屏构图成立 + 真实交互成立 + 真实数据规模成立。**

## 1. 复盘口径

### 1.1 证据来源

- 当前对话中用户逐轮确认、纠偏和实机截图；
- `interaction-visual-acceptance-ledger.md` 中保留的验收记录及第 25 节对旧 `READY` 结论的撤销；

- 真实 Electron / 浏览器截图与用户实机截图；
- 既有视觉验收文档中“无溢出、测试绿、页面存在”等结构性结论。

### 1.2 计数方法

下文次数是**保守下限**，按用户明确提出的一轮反馈计一次；同一轮同时暴露多个问题时会进入多个类别。它不是情绪统计，而是用来识别哪些约束没有被内化。

### 1.3 失败分类总览

| 用户要求复盘的类别 | 保守结论 | 说明 |
|---|---:|---|
| 重复坑 | **10 个模式家族** | 下面第 3 节合计至少 88 次“模式命中”；同一反馈可能同时命中密度、父布局和质感，不能当作 88 个独立 bug |
| 一次性但严重的盲区 | **12 项** | 任一项都足以否定当前页面或内测状态，例如错误版本号、窗口控件叠加、本子无生命周期、失败不可恢复 |
| 过度工程 / 过度测试 / 过度防御 | **至少 6 类** | 哈希与重复 review、低风险边角测试、过重功能结构、复杂 Skill 流程、缺少停止规则、无正收益并行 |
| 视觉验收失真 | **至少 6 种机制** | 局部代替整体、无溢出代替美观、空 fixture、只看 renderer、竞品只“看过”、审计倾向证明成功 |
| 交互主链路漏验 | **至少 10 轮明确反馈** | 搜索、设置、成果主行、AskUser、`@`、新建对话、菜单、重试等存在“看得见但点不通” |
| 产品心智误解 | **至少 8 轮明确反馈** | 搭子/工作台混淆、通知过重、定时任务日历化、待办删除过重、计划与权限混排等 |
| Subagent 编排问题 | **4 个流程问题** | 为开而开、共享文件踩踏风险、决策碎片化、审计提示偏向给高分而不是证伪 |

这个数字说明问题不是“漏了几个细节”，而是同一批判断错误在不同页面反复出现。真正需要修的是工作协议，而不只是继续增加局部 patch。

## 2. 事实时间线：从用户要求到实际偏差

| 阶段 | 用户明确要求 | 实际偏差 | 暴露的流程问题 |
|---|---|---|---|
| 启动纠偏 | 三小时没有实质产出；清理 C 盘；默认临时数据放 E 盘；Skill Hub 不要哈希、反复 review 和过度防御 | 任务被安全验证、哈希、重复检查和复杂流程拖慢，且过程文件占用 C 盘 | 把低风险任务按生产事故标准处理；没有先定义“正常主链路够用”的停止条件 |
| Skill Hub 产品化 | 扫描竞品 Skill Hub；做中文用途名；精选 Skill 直接内置/可下载；普通用户不应看到仓库式命名 | 开始从开发者视角组织元数据，界面扁平，详情薄，官方 Logo 和标签交互不完整 | 数据工程视角压过了用户识别与选择心智 |
| 便签 / 待办工作台 | Alt+N 可配置；默认便签、可转待办；富文本、图片、文件、链接、@引用；独立工作台视图；后台常驻和路径不挤爆 C 盘 | 前期讨论花费过长，部分边缘分支先于主链路；后续视觉设计又出现过重面板和不必要日历 | 没有先冻结一条最短可用旅程，再扩展能力 |
| 视觉设计收敛 | 逐页、逐步确认；Image 设计稿为最终视觉依据；组件对应各自权威稿；允许更有品牌感但不幼稚 | 设计稿之间出现漂移，落地时没有建立“组件—权威稿”映射；后续误把某页面的侧栏或壳层当全局标准 | 缺少权威来源索引和冲突裁决规则 |
| momo / Logo | Logo 抽象专业，momo 作为具体人格；momo 可爱但克制，不要恐怖谷、熊孩子、多动过度；用户消息无头像，momo 头像小 | 多次出现过度具象、恐怖简笔画、头像过大、动效设想过头 | 把用户给出的气质边界当作单次美术反馈，没有沉淀为人格视觉约束 |
| 工作台 / 搭子态 | 工作台冷中性高密度；搭子态暖、轻、陪伴，不带工作台侧栏；两个模式共享能力但心智不同 | 一度把搭子态做成“无复杂 UI 的工作台”；后续工作台又全灰白、过疏、像老人机 | 只复用结构，没有守住模式的信息密度与关系心智 |
| 输入框与菜单 | 参考 Codex / ChatGPT；`+` 单列上展；`/` 独立图标；`@` 真引用；计划模式从 `+` 进入；权限三档独立；空间不足退化为图标；无语音能力就不展示麦克风 | 菜单曾向下展开并顶动输入框；计划和权限混排；文字挤压；`/` 基线漂移；出现未接语音图标；控件看起来能点但无功能 | 未建立 composer 状态矩阵与能力真值检查 |
| 过程与可信性 | 工具卡默认折叠，但展开必须显示原始命令、cwd、stdout/stderr 和报错；计划/待办必须准确；subagent 显示初始 prompt 并明显区分 | 一度用摘要重复摘要；过程卡片只有标题，没有原始运行细节；subagent 头像设计怪异 | 把“信息更少”误解为“更高级”，忽略可验证性 |
| 审批与失败 | 普通缓存清理不应红色重审批；真正不可逆行为才高危；两分钟超时拒绝；失败要重连、重试、保留部分输出并给重试按钮 | 普通失败一度彻底中止；错误回执过重；审批风格泛红；重试语义没有完整验收 | 没有按可逆性和副作用分类失败与审批 |
| 成果与文件 | 成果回执不能撑爆整屏；多文件用矮行；长报告放普通回答；成果主行单击打开；Explorer 在编辑器右侧；PDF 不应被四栏压窄 | 成果主行曾不能点；结果卡过高；Explorer 位置错误；四栏压缩 PDF；甚至提前设计未兑现的 XLSX 编辑 | 先画功能存在，再检查主动作和真实能力边界 |
| 设置与浮层 | 设置单列、可折叠而不是深层跳转；通知只是铃铛浮窗；用量 hover 小浮窗；开关左右明确；模型/权限菜单向上且不推布局 | 设置入口曾进空白页；通知互相遮挡；用量插入正文顶开上下文；开关圆点卡中间；菜单向下被裁切 | 只检查默认静态态，没有验 open / collision / dismiss / keyboard / viewport |
| 真实工程验收 | 每页截图，和对应权威稿比较；主开发亲自目验；只保留一个独立只读视觉审计 | 曾宣布 `READY / 90%+`，后来被真实用户数据和截图推翻；多处仍需用户逐个指出 | 审计提示和验收指标偏向“证明已完成”，没有要求主动证伪 |
| 当前再次暴露 | 移除重复折叠键后，整体布局仍应均衡 | 新建对话按钮只占半截，右侧留白；开发验收未发现 | 典型“局部 patch 验收”，没有父布局和整屏复核 |

## 3. 重复坑：保守次数与典型表现

| 重复坑 | 保守下限 | 典型表现 | 为什么是重复而不是偶发 |
|---|---:|---|---|
| 尺寸、密度和空间比例失衡 | **至少 14 次** | 大状态卡浪费中心区；momo 头像过大；Skill 图标/卡片过大；消息引导卡过高；成果卡撑屏；PDF 被多栏压窄；设置/侧栏像老人机；新建对话半截宽 | 用户持续用“太大、太空、太疏、太挤、信息密度低”纠偏，说明没有形成统一密度尺 |
| 局部修复后未复核父布局 / 整屏构图 | **至少 8 次** | 删除组件后留死空白；折叠栏后其他按钮被挤；输入框某一项修好但基线仍漂；四栏局部都存在但中心内容不可读；模型菜单打开时整体被顶 | 验收对象长期停留在被改 DOM，而不是其父容器、兄弟元素和整屏视觉重心 |
| 扁平、廉价、缺少层次与高级感 | **至少 9 次** | 选中态大块浅蓝；黑粗原生输入框；供应商卡片像占位；Skill Hub 过平；按钮没有细节；发送按钮像廉价益智游戏；工作台绝望灰白 | 已有多轮“高级感”要求，但没有把层级、材质、状态、排印转成 token 和比较指标 |
| 浮层方向、碰撞、遮挡与 reflow 错误 | **至少 7 次** | 模型菜单向下展开；权限菜单挤动输入框；通知弹层互相遮盖；本子菜单在窄滚动区被裁切；用量插块顶开消息；特色功能与引导队列争位置 | 只验菜单内容，不验锚点、viewport、滚动容器、叠层和关闭路径 |
| “看得见但点不动 / 点了不生效” | **至少 10 次** | 搭子搜索不能点；设置空白；Skill 详情标签不切换；成果主行不打开；AskUser 漏调用；`@` 没有引用菜单；新建对话失败无反馈；若干入口只是摆设 | 单测常验证元素存在，未覆盖真实 Electron 点击、状态变化和重启恢复 |
| 图标/视觉符号脱离信息语义 | **至少 9 次** | Skill 无意义大图标；定时任务强行分类图标；subagent 恐怖头像；供应商伪 Logo；未实现语音却展示麦克风；发送按钮过度游戏化；窗口控件重叠 | 没有执行“图标必须传递稳定语义，否则缩小/取消”的规则 |
| 产品心智过重、过正式或放错层级 | **至少 8 次** | 通知中心做太重；待办删除进入正式回收站；定时任务做日历；心迹首发过重；搭子态带工作台侧栏；计划模式与权限混在一起；大思考状态卡占中心 | 把功能清单直接翻译成页面，而不是先判断用户在当前场景的动作重量 |
| 权威稿和实现映射漂移 | **至少 6 次** | Skill Hub 稿误带到主界面；同一设计稿非目标区域被误当权威；输入框回退到非定稿样式；Explorer 左右位置混淆；多版 logo/momo 语义串线 | 没有保存“这张图只权威决定什么、不决定什么” |
| 真实能力边界没有守住 | **至少 5 次** | 提前展示 XLSX 编辑；展示未接语音；计划/目标模式只画 UI 未接底层；连接器或搜索服务看起来已支持但底层待做；文件/工具按钮无真实行为 | 用视觉稿或组件存在制造能力心智，没有 capability gate |
| 用户已经定下的约束未内化 | **至少 12 次** | 仍反复出现大卡、大头像、向下菜单、灰白低密度、文字挤压、假按钮、过度验证、过多 subagent | 反馈被当作当前 patch 指令，没有抽象成以后所有页面都适用的规则 |

## 4. 一次性但严重的盲区

这些问题未必重复很多次，但单次就足以否定“可内测”或“已验收”：

1. **C 盘过程数据膨胀**：违背用户明确的系统盘保护要求；说明临时目录、缓存和截图没有统一根目录策略。
2. **版本号显示为 `43.2.0`**：读取了 Electron 运行时版本而非 Leemo 自身 SemVer，属于发布身份真源错误。
3. **原生窗口控件和自绘控件叠加**：用户看到双最小化、双最大化、双关闭，且关闭区成为竖长红条；说明只看 renderer 截图，没有验证系统窗口层。
4. **本子永久绑定、无归档/移除/重定位**：真实本地文件夹一旦接入就可能永久撑爆侧栏，是基本对象生命周期缺失。
5. **真实网络失败没有合理恢复**：轻微波动即可整轮终止，又没有紧凑重试入口；直接破坏核心 Agent 主链路。
6. **搭子搜索不可用、设置空白页**：最普通的可见入口都没有走完真实旅程。
7. **成果列表主行不能打开**：核心产出被藏在小图标动作里，违背用户对“主对象单击即查看”的预期。
8. **AskUser 应调用时漏调用**：结构化问询可靠性没有协议约束，用户体验会在同一流程中随机退化。
9. **供应商使用疑似自造 Logo**：既损害信任，又存在品牌表达风险；官方资源核验应在上屏前完成。
10. **未实现能力产生假 affordance**：例如语音图标、XLSX 编辑器，用户会自然认为可以使用。
11. **PDF 只按“能渲染”评估**：用户要求文字选择、复制格式、搜索、长文档和浏览器级体验；仅有 PDF.js 依赖不等于达到验收标准。
12. **旧 `READY` 被真实用户数据推翻**：这是流程级事故。台账已明确撤销此前结论，证明验收样本、指标和审计提示都不可信。

## 5. 过度工程、过度测试与过度防御

### 5.1 已发生的问题

- 下载普通 Skill 时反复计算哈希、review 拷贝结果，把可恢复的文件下载按高危供应链事件处理；
- 三小时投入却没有与投入相称的可见产出；
- 为边角 case 编写大量测试和防御分支，而主链路、视觉和真实点击仍有明显缺陷；
- Skill Hub 先处理复杂版本、哈希、扫描逻辑，晚于用户最需要的“名字、简介、链接、卡片、安装”；
- 为通知、定时任务、心迹、回收等功能设计过重结构，增加后续实现和验收面；
- 一度希望多开 subagent，但任务共享状态、设计决策耦合，反而增加汇总和冲突成本。

### 5.2 根因

1. **可量化的验证更容易获得“做完了”的心理确定性**：哈希、测试数、类型检查、无溢出都比审美判断容易，因此被过度使用。
2. **错误风险权重失真**：把普通内测 UI bug 与数据破坏、密钥泄漏按相同等级防御。
3. **缺少停止规则**：没有在任务开始前明确“主链路通过 + 两个真实视口 + 无 P1 即停”，导致检查不断扩张。
4. **以工程复杂度补偿视觉不确定性**：不会判断整体质感时，转向编写更多代码和测试，产生“忙但没有更接近用户目标”的假进展。

### 5.3 新边界

- TDD 只锁定会反复回归的**行为、语义和关键几何**；不为每个阴影、颜色、像素值写脆弱测试。
- 可恢复的内测视觉问题允许存在 P2；主链路断裂、数据丢失、密钥泄漏、不可逆写入仍是强闸门。
- 普通拷贝只验证文件存在、基本可读、版本/来源元数据；除非涉及不可信二进制或发布完整性，不做反复全量哈希。
- 每个开发纵切先产出可见结果，再补最小回归；禁止先建设大而全框架。

## 6. 思维盲区与因果链

### 6.1 “用户说 A”被缩成“改 DOM A”

因果链：

`用户指出重复折叠键挤压新建对话` → `只删除重复按钮` → `测试断言按钮数量为 1` → `未检查原操作行重新布局` → `新建对话仍只占半截，留下死空白`。

缺失动作：修改后必须检查父容器、兄弟元素、负空间、视觉重心和交互热区。

### 6.2 把“没有坏”当成“好看”

因果链：

`无横向溢出 / 输入框在视口 / 控件未裁切 / 测试绿` → `宣布视觉统一和 READY` → `真实用户一眼看到老人机密度、扁平卡片、死空白、低对比选中态`。

缺失动作：结构健康门只判断“不坏”；视觉门必须另外判断比例、节奏、层级、信息密度和品牌气质。

### 6.3 空 fixture 掩盖真实产品问题

因果链：

`使用 1–2 条会话、少量本子、单张成果截图` → `侧栏看起来没有溢出、卡片看起来不拥挤` → `真实用户有长列表、失败、弹层、多个本子后，生命周期和空间问题集中爆发`。

缺失动作：必须用规模 fixture（至少 8 本子、20 会话、多文件结果、长工具输出、失败态）验收。

### 6.4 竞品参考停留在“看过”

因果链：

`截了 Codex / NewMax / Kimi` → `模仿了某些图标、颜色或卡片` → `没有记录其顶栏高度、行密度、弹层锚点、每屏容量、状态反馈` → `Leemo 元素齐全但仍显粗糙和稀疏`。

缺失动作：竞品对照必须产出几何表、状态表和“为什么”说明，而不是灵感拼贴。

### 6.5 验收提示倾向证明成功，而不是主动证伪

因果链：

`实现完成后让审计者打分` → `审计者围绕已改页面确认要求存在` → `没有主动寻找最多三个能否定 READY 的问题` → `高分和 READY 被用户实机截图推翻`。

缺失动作：独立审计必须以“找到失败证据”为目标，先列 P0/P1/P2，再决定是否 READY。

### 6.6 反馈没有上升为可复用规则

因果链：

`用户指出一次大图标` → `缩小这一页图标` → `下一个页面又出现大而无信息的图标`；

`用户指出一次菜单向下` → `修这一菜单` → `另一个菜单仍向下并裁切`；

`用户指出一次灰白稀疏` → `增加局部颜色` → `全局密度仍像老人机`。

缺失动作：每条用户反馈必须同时产生“本页修复”和“一条全局不变量”。

## 7. 新工作协议（强制执行）

### 7.1 设计权威映射

每个视觉任务先维护一张表，未完成不得写 CSS：

| 字段 | 内容 |
|---|---|
| 页面 / 组件 | 例如工作台左侧栏 / 新建对话操作行 |
| 权威稿 | 具体图片绝对路径或已批准稿 ID |
| 权威范围 | 这张稿只决定哪些区域、状态和比例 |
| 非权威范围 | 图中哪些元素属于其他步骤、不得沿用 |
| 最新用户纠偏 | 例如“只有一个折叠入口；主操作不得留下半截死空白” |
| 真实能力边界 | 哪些按钮已接线；未接能力必须隐藏 |
| 验收视口 / 数据 | 1440、1280、1024；空态与规模态 |

规则：**一张设计稿不能自动成为整页权威；它只对用户当步确认的目标部分有权威性。**

### 7.2 三层视觉验收

#### 第一层：微观组件

- 字号、字重、行高、图标尺寸、圆角、边框、阴影是否协调；
- 默认、hover、focus-visible、pressed、selected、disabled、busy、error 是否完整；
- 光学中心是否对齐，而不仅是 DOM box 中心；
- 图标是否表达稳定语义，是否真的需要；
- 点击热区可用但不可视觉膨胀。

#### 第二层：父布局与局部构图

- 修改、删除、折叠组件后，父容器是否重新分配空间；
- 兄弟元素是否被挤压、漂移或留下死空白；
- 主操作、次操作、状态和快捷键的视觉权重是否符合动作优先级；
- 弹层是否相对正确触发器定位，是否撞 viewport、顶栏、侧栏和滚动容器；
- 当前区域的信息密度是否与相邻区域一致。

#### 第三层：整屏产品视觉

- 在 100% 缩放下先看整屏 3 秒：焦点落在哪里，是否符合页面主任务；
- 负空间是否有意图，还是“组件没撑满后的空洞”；
- 每屏可见对象数量是否接近权威稿和竞品；
- 工作台与搭子态的模式气质是否明确但仍属于同一品牌；
- 长内容、滚动到底部、菜单打开和失败态下是否仍成立。

三层必须全部通过。第一层通过不能抵消第二、三层失败。

### 7.3 真实交互旅程

每个可见入口必须记录：

1. 用户从哪里看到它；
2. 点击 / 键盘后状态如何变化；
3. 成功结果在哪里；
4. 失败时如何恢复；
5. 需要持久化的状态重启后是否存在；
6. 未配置模型、目录失效、网络波动等常见失败是否有人话反馈；
7. 入口若无真实能力，是否应该隐藏而不是占位。

禁止只写“按钮存在”或“组件渲染成功”。

### 7.4 删除 / 隐藏组件后的父布局复核（新增硬闸门）

每次删除、收起或隐藏一个元素，必须执行：

- 截取修改前局部与整屏；
- 删除后检查父容器剩余宽高如何重新分配；
- 检查主操作是否应 `flex: 1`、居中、靠边或与快捷键分区；
- 检查是否出现无意义空白、断裂分隔线、孤立按钮、视觉重心偏移；
- 在最宽和最窄目标视口都检查；
- 再截取局部与整屏；
- 只有“删除目标消失 + 父布局成立”才算完成。

当前“新建对话半截宽”必须按此闸门重新验收，而不是再只调一个 width 数值。

### 7.5 截图矩阵

每个主页面至少需要以下矩阵，不得只交一张空态：

| 维度 | 必须覆盖 |
|---|---|
| 视口 | 1440×900、1280×800、1024×768；必要时 720×640 只做可用性底线 |
| 数据 | 空态、正常真实数据、规模数据（8 本子 / 20 会话 / 多文件 / 长输出） |
| 滚动 | 顶部、中段、底部 |
| 状态 | 默认、选中、hover、键盘焦点、打开浮层、失败、重试、完成 |
| 模式 | 工作台与搭子态分别验收，不互相代替 |
| 壳层 | renderer 页面截图 + 真实 Electron 整窗截图；涉及系统标题栏必须看整窗 |

每张截图旁必须写一句“本图要否定什么问题”，防止截图沦为存档。

### 7.6 TDD 边界

**应该测试：**

- 点击是否触发真实动作；
- 状态、持久化和失败恢复；
- 弹层不 reflow、会 flip/shift/clamp；
- 开关语义和明确左右状态；
- 单一折叠入口；
- 关键几何底线（例如顶栏、行高、控件中心线、无裁切）；
- 主对象整行可点击和键盘可达。

**不应该过度测试：**

- 每个 CSS 数值和阴影字符串；
- 可由一张真实截图更快识别的审美细节；
- 低风险、可恢复、用户主链路之外的所有排列组合；
- 为“看起来全面”而重复验证同一复制、同一哈希和同一构建产物。

停止规则：focused tests 绿、真实主旅程通、截图矩阵无 P0/P1 后停止；P2 进入明确 backlog，不扩散为架构重写。

### 7.7 Subagent 正收益门槛

只有同时满足以下条件才开 subagent：

- 输入边界独立，不需要频繁同步主线程决策；
- 不修改与主线共享的视觉/CSS 文件；
- 预计实际节省至少 30 分钟墙钟时间；
- 输出物清晰（例如只读竞品几何表、只读最终审计）；
- 有唯一主决策者负责合并结论；
- 它不只是为了“看起来并行”。

视觉实现阶段只允许一个只读审计者。其提示必须是：

> 先寻找能否定 READY 的证据；逐项报告 P0/P1/P2、对应截图和量化差距；不得改代码，不得以测试通过作为视觉结论。

共享 CSS、主壳、输入框等高耦合区域不得并行多人修改。

## 8. 每次视觉任务完成前的可勾选清单

### A. 权威与能力

- [ ] 已写清本组件对应哪一张权威稿、权威到什么范围。
- [ ] 已记录最新用户纠偏，旧稿冲突处没有误继承。
- [ ] 所有可见按钮都对应真实能力；未实现能力已隐藏。
- [ ] 文案使用用户语言，不暴露内部协议/模型术语。

### B. 微观组件

- [ ] 字体、字号、字重、行高、图标和按钮比例协调。
- [ ] 光学中心与基线一致，不只看 flex 居中。
- [ ] hover / focus / pressed / selected / disabled / busy / error 状态齐全。
- [ ] 图标表达真实信息；无意义图标已取消或缩小。
- [ ] 输入框没有浏览器默认黑粗边、双重 focus ring 或廉价大阴影。

### C. 父布局

- [ ] 改动后检查了父容器、兄弟元素和剩余空白。
- [ ] 删除/隐藏元素后没有死空白、断裂分隔线或孤立控件。
- [ ] 主操作占据合理宽度并保持清晰优先级。
- [ ] 文字在空间不足时按优先级隐藏为图标，不换行破坏排版。
- [ ] 弹层不推挤正文，且不会被 viewport / rail / scroll 容器裁切。

### D. 整屏

- [ ] 3 秒扫视时主任务焦点明确。
- [ ] 负空间有意图，而不是内容缺失造成空洞。
- [ ] 每屏可见对象数量与权威稿 / Codex / NewMax 同视口对照过。
- [ ] 工作台不全灰白、不过疏；搭子态温暖但不幼稚。
- [ ] 空态、真实数据和规模数据都看过。

### E. 真实交互

- [ ] 主入口通过鼠标和键盘真实点击。
- [ ] 成功、失败、重试、取消、关闭、重启恢复都按风险比例验证。
- [ ] 主对象整行可点击，不把主动作藏进小图标。
- [ ] 菜单打开方向、层级、碰撞、Escape、焦点回归均真实验证。
- [ ] console/page error 为 0，或已记录真实已知问题。

### F. 截图与审计

- [ ] 1440、1280、1024 三视口截图完整。
- [ ] 至少一张真实 Electron 整窗图，而不只是 renderer 内容。
- [ ] 每张截图说明它在验证 / 否定什么。
- [ ] 主开发者先主动列出至少 3 个仍可能不好的点并逐一关闭或降级。
- [ ] 独立审计者以证伪为目标，P0/P1 均为 0 后才允许 READY。

## 9. 如何减少用户再次充当 QA

### 9.1 用户反馈必须产生两份结果

每条反馈不只改当前页面，还要落成：

1. **本地修复项**：具体组件、路径、验收截图；
2. **全局不变量**：以后所有页面都要遵守的规则。

示例：

- “菜单不要向下顶输入框” → 本地修模型菜单 + 全局所有 composer 浮层必须锚定上展且不 reflow；
- “新建对话按钮只剩半截” → 本地重做操作行 + 全局删除组件后必须检查父布局；
- “发送按钮像幼儿园游戏” → 本地降饱和与体积 + 全局主动作禁止高光球体和玩具渐变；
- “Skill 大图标无意义” → 本地缩小 + 全局图标尺寸随信息量而定。

### 9.2 主开发先做“反对者检查”

在给用户看之前，主开发必须回答：

- 如果我是第一次使用，这里哪个按钮最像假的？
- 哪块空白没有目的？
- 哪个元素比它的重要性大得不合理？
- 真实数据多五倍后哪里先崩？
- 鼠标点开哪个菜单最可能被裁切或顶动布局？
- 删除刚改的元素后，其父容器有没有重新构图？
- 与同视口 Codex / NewMax 放在一起，Leemo 哪一眼最像老人机或 demo？

无法回答这些问题，就不能让用户开始目验。

### 9.3 不再使用模糊的完成话术

禁止：

- “视觉已经达到 90%+”但没有量化表；
- “完全复现”但只有元素存在；
- “全部打通”但没有真实点击记录；
- “READY”但仍有未跑的真实数据、失败、重启或弹层矩阵。

改用：

- 已验证哪些视口、数据量和旅程；
- 仍有哪几个 P2；
- 哪些只在浏览器 fixture 验证，哪些在真实 Electron 验证；
- 哪些是实现、哪些是集成、哪些是 release-verified。

### 9.4 当前问题的直接验收口径

“新建对话”操作区的下一轮验收，不是“按钮变宽了”即可，而是：

- 顶栏只保留一个侧栏折叠入口；
- 侧栏首行只有一个清晰主动作；
- 主动作使用可用横向空间，不留下与任何操作无关的大片空白；
- `Ctrl N` 作为次级提示靠右但不挤压主标题；
- 在 1440 / 1280 / 1024 三视口与展开/收起状态都保持均衡；
- 下方本子区与首行的边界、间距、色彩层级连续；
- 整屏截图与局部截图都通过，而不是只截图被改按钮。

## 10. 新的完成定义

一个 Leemo 页面只有同时满足以下条件，才允许标记完成：

1. **语义正确**：符合用户场景和产品心智，不把轻操作做重，不把模式混淆。
2. **能力真实**：看得见的入口均可用，失败可理解、可恢复；未实现能力不上屏。
3. **组件精细**：排印、图标、状态、动效和控件比例成立。
4. **父布局成立**：增删改组件后，局部构图和负空间仍有意图。
5. **整屏成立**：同视口、同数据量下，密度、层级和重心不输给权威稿的基本水准。
6. **规模成立**：长列表、多文件、长输出、错误、菜单和底部状态不崩。
7. **证据成立**：真实 Electron 点击、重启和截图矩阵，而非只靠单测或 fixture。
8. **审计成立**：主开发主动证伪，独立审计无 P0/P1；审计分数不能覆盖真实缺口。

## 11. 必须长期记住的十条禁令

1. **禁止**把“元素已移除”当作完成；必须看移除后的父布局。
2. **禁止**把“测试绿、无溢出”当作视觉好看。
3. **禁止**只用空 fixture 证明信息密度和长列表体验。
4. **禁止**展示没有真实接线的图标、按钮或能力。
5. **禁止**让 composer 菜单向下顶动输入框或被局部容器裁切。
6. **禁止**把某张设计稿非目标区域误当全局权威。
7. **禁止**用大图标、大卡片、大留白假装高级感。
8. **禁止**用测试数量、哈希和重复 review 掩盖主链路与视觉不确定性。
9. **禁止**让多个 subagent 同时修改共享视觉区域；审计者只读且以证伪为目标。
10. **禁止**在用户实机完整旅程前宣布 `READY / 完全复现 / 90%+`。
