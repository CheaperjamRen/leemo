# ColaOS 1.2.6 实机复盘：Leemo 应该学什么，不该学什么

**审计日期**：2026-07-30

**实机版本**：`E:\Cola\Cola.exe`，File/Product Version `1.2.6.225`

**对照对象**：当前分支上的 Leemo 搭子态、工作台态、设置、成果与 Skills 入口

**研究目的**：判断 ColaOS 新版哪些设计能帮助 Leemo 成为“一个认识我的人 + 一套完整 Agent 能力”，而不是追着竞品堆功能。

## 一、证据边界

本轮逐页目验了 ColaOS 的桌面首页、Chat、Coding、觉知、技能（市场 / 已安装 / Channels）、智能闹钟，以及设置中的基础设置、用量、网络、隐私和记忆迁移。

- 使用的是用户已安装、已登录的真实客户端，不是官网截图或旧印象。
- 为保护用户额度和外部数据，本轮没有发送新的模型任务、没有安装技能、没有连接 Channel，也没有创建真实闹钟。
- 任务完成/失败体验的判断来自现有历史记录和界面结构，不等同于本轮重新跑过一次付费任务。涉及这部分的结论均按此边界表述。
- 点击“快速创建”只观察到聊天框预填自然语言请求，随后已清空，没有发出。

## 二、先说结论

ColaOS 最值得学的不是插画、猫或某个具体页面，而是它让用户先感到“这里有一个持续存在的关系”，再去发现 Chat、Coding、闹钟和技能。当前 Leemo 已经守住了更重要的底座：同一个 momo、同一份对话/记忆/文件/成果、同一套完整 Agent 能力，只换搭子态和工作台态两个壳。这个优势不能为了模仿 ColaOS 而丢掉。

Leemo 当前搭子态的主要缺口也因此很明确：它已经是一个温暖、干净、Markdown 正常渲染的聊天界面，但用户还看不见“momo 为什么认识我、记住了什么、哪些事准备以后跟进”。关系感目前主要靠语气和形象表达，尚未形成可验证的连续关系。

下一步应先补 **可信的关系连续性**，不是再做一轮纯视觉换皮。

## 三、逐页观察

### 3.1 桌面首页：关系身份是第一屏信号

ColaOS 用整窗场景插画、中央语音入口和底部 Dock 构成“回到房间”的心智。Chat、Coding、觉知、技能、智能闹钟和设置都从同一空间进入。优点不是画面本身，而是用户一打开就知道自己面对的是一个持续存在的角色，而不是工具列表。

Leemo 的搭子空状态已有时段问候、momo 形象和建议问题，比普通 Chat 更有温度；但进入历史长对话后，关系身份很快退化成“居中的消息流”。缺少一个始终可达的连续性入口。

### 3.2 Chat 与交付：聊天之外还有可复用结果

ColaOS Chat 保持轻量，同时把“查看全部交付”作为稳定的右侧入口，支持搜索和重访。它在用户心智上区分了聊天过程与可复用结果。

Leemo 已有共享的成果页、文件预览和任务连续性，能力底座不弱；搭子态只是没有把成果做成常驻重面板，这与“轻过程”定位一致。这里应吸收的是**交付可回看**，不是把工作台侧栏强塞进搭子态。

### 3.3 Coding：清晰分工，但不能复制数据割裂

ColaOS Coding 是独立的密集执行面：项目/会话列表、引擎、模式和固定输入区都比 Chat 更像工作台。这种模式边界清楚，值得参考。

但它的 Chat/Coding 分区也暴露出跨模式连续性容易断裂的问题。Leemo 的双壳共享 store、同一对话可原地切换并继续，是更符合产品宪法的做法。任何后续功能都必须先落共享层，不能在搭子态和工作台态各造一份数据。

### 3.4 觉知：强关系感，也最容易越界

“觉知”用日期卡、温暖插画和第一人称长文，把一段时间的互动组织成“它注意到了我的生活轨迹”。详情以海报式弹层呈现，关系感很强。

风险同样明显：长篇主观叙事很容易把模型推断包装成事实，用户也缺少清晰的来源、置信度和纠错入口。momo 可以有判断，但不能擅自改写用户的人生故事。

Leemo 若吸收，只能改造成**有来源的 momo 观察**：标明来自哪次对话/哪份本子、发生日期、是用户原话还是 momo 的推断，并允许用户纠正、删除或回到原对话。插画与自动长文不是当前必需。

### 3.5 Skills：发现体验好，但“已启用”必须等于可用

ColaOS 的市场采用预览图、分类、官方/社区标识，发现和理解能力的成本低；已安装页用紧凑分组和开关管理；Channels 还能连接本地插件、飞书、Telegram、微信。

实机也出现了 Windows 上 Apple Calendar / Notes / Reminders 显示已启用的情况。这说明市场与开关做得漂亮，不代表平台依赖已经打通。

Leemo 后续可吸收技能目录的信息架构，但必须把“安装、启用、当前平台可运行、真实调用成功”分开验收。现阶段优先打通 Claude Code 原生 Skills/MCP/Subagent 能力，不先造大型市场。

### 3.6 智能闹钟：用自然语言表达主动性

智能闹钟同时提供“我的闹钟”和案例库，覆盖晨间待办、每日总结、变化追踪、邮件摘要、天气、复盘等场景。最值得学的一点是：点击“快速创建”后没有先弹复杂表单，而是回到 Chat 并预填“帮我设置一个定时提醒”，让用户继续用自然语言补充和确认。

这很适合 momo。Leemo 的主动性应先表现为“答应以后跟进什么、什么时候跟进”，并用对话形成意图；不必第一步就做一套后台自动化管理系统。没有可靠调度和失败恢复前，也不能用文案假装会主动提醒。

### 3.7 设置：成熟的信息架构与低摩擦迁移

ColaOS 设置采用全屏左导航 + 右内容区，分类清楚。值得记录的细节包括：

- 基础设置有语言、外观、字体、Markdown 实时渲染、首页回复、硬件加速和音频设备。
- 记忆迁移支持 ChatGPT、Gemini、Claude Code、Cursor、OpenClaw 自动导入，也支持文件、文件夹和粘贴；手动路线会给旧 AI 一段整理提示词，再把结果送回对话确认。
- 网络设置提供 HTTP 代理、地址、端口、认证、绕过列表、保存和诊断。这与 Leemo 用户真实使用手动代理的场景高度相关。
- 用量页按动作展示消耗，降低“这次为什么花了这么多”的不确定感。
- 隐私页主要是匿名数据开关和协议，没有看到与记忆同等清晰的审计/纠错能力。

Leemo 当前已经采用中型设置面/左导航右内容，不需要照抄外观；应补的是记忆可见性、迁移的对话式流程，以及后续的代理诊断。代理设置是明确待办，但不应插队本轮关系连续性。

## 四、对照 Leemo 当前状态

| 维度 | ColaOS 1.2.6 | 当前 Leemo | 判断 |
|---|---|---|---|
| 第一屏关系感 | 很强，空间与角色先于工具 | 空状态有 momo 与问候，长对话后变弱 | Leemo 需要稳定的连续性入口，不必复制整窗插画 |
| 双模式 | Chat / Coding 边界清楚，但连续性有割裂风险 | 同一对话、记忆、成果和能力原地换壳 | 保留 Leemo 方案 |
| 记忆呈现 | 有迁移和“觉知”，但来源/纠错弱 | 本地 Markdown 真落盘，可打开目录；应用内几乎不可见 | 下一张卡应补可见、可追溯、可纠错 |
| 主动跟进 | 闹钟案例成熟，创建回到自然语言 | 只有零散提醒/通知心智，未形成可靠闭环 | 先做对话意图与可见承诺，再做调度 |

## 五、吸收 / 改造后吸收 / 不吸收

### 直接吸收原则

1. **关系身份是搭子态第一屏信号**：momo、最近的共同上下文、待跟进事项要比功能目录更早出现。
2. **自然语言创建主动任务**：先让用户说清楚意图，再在必要时补结构化确认。
3. **记忆迁移走对话确认**：导入前给用户看整理结果，不静默吞入长期记忆。
4. **设置按用户问题分区**：模型、通用、个性化、连接器、权限/隐私分别承载清晰任务。
5. **交付结果可搜索、可回看**：已有成果页继续作为共享真源。

### 改造后吸收

1. **觉知 → momo 观察**：保留“它注意到了我”的价值，增加来源、日期、事实/推断标记、纠正、删除和原对话入口。
2. **智能闹钟 → 待跟进**：先做用户可见的承诺清单和自然语言创建；可靠调度、重启恢复、失败通知验证通过后，才宣称会主动提醒。
3. **技能市场 → 场景技能目录**：学习/求职优先，展示平台与依赖检查；“已安装”不等于“可运行”。
4. **Chat/Coding 分区 → 双壳同底座**：吸收清晰的信息密度差异，拒绝会话、记忆或能力割裂。
5. **用量页 → 用户可理解的成本**：把 Provider、模型、动作和估算费用对应起来，保持 BYOK。

### 明确不吸收

1. 不把全屏插画房间当成当前核心开发目标。
2. 不为“陪伴感”自研封闭的记忆数据库或第二套人格数据。
3. 不自动生成没有证据、不可纠正的情绪日记和人生结论。
4. 不默认启用当前平台无法运行的技能。
5. 不让搭子态丢失 Tools、MCP、Skills、Subagent、浏览器或 Coding 能力。
6. 不引入付费云账户、平台积分锁定或持续后台耗费模型额度的默认行为。

## 六、下一张开发卡：R2 可信关系连续性

### 用户问题

用户现在知道 momo “声称会记得”，但无法在应用内快速回答：

- momo 现在究竟记住了我什么？
- 这条从哪里来，是我说的还是它猜的？
- 记错了，我怎么改或删？
- 它答应以后跟进的事在哪里？

### 最小范围

先做现有 `~/Leemo/CLAUDE.md` 与 `~/Leemo/memory/` 的安全可视化，不创造新记忆引擎：

1. 搭子态提供稳定但克制的“momo 记得”入口。
2. 应用内展示现有记忆文件、更新时间、真实路径和 Markdown 内容；缺失/空文件诚实显示。
3. 用户可编辑并保存，也可打开原文件/目录；写入只允许既定记忆文件，带并发修改保护，不能越过本地目录边界。
4. 明确区分“用户事实 / 偏好 / 进度 / 重要时刻 / 收藏”，不把模型推断伪装成已确认事实。
5. 搭子态和工作台态读取同一份数据；修改后新对话按现有加载路径生效。

### 验收口径

1. 从搭子态两步内能看到 momo 当前真实读取的记忆，而不是演示数据。
2. 修改一条记忆并保存，关闭再打开仍存在；新对话能读到修改后的内容。
3. 外部编辑文件后，界面能检测冲突并要求刷新，不能静默覆盖。
4. 不允许通过构造 id/path 读取或写入 `~/Leemo` 之外的文件。
5. 没有记忆、文件损坏、读取失败、保存失败都有用户可理解的状态。
6. 两种模式和重启后看到同一份结果。

### 后续而非本卡

- 对话证据自动回链与事实/推断置信度。
- 记忆迁移向导。
- “待跟进”的可靠调度、重启恢复和失败通知。
- 自动生成配图或长篇关系回顾。
- Skills 市场、Channels、广泛第三方账号接入。

## 七、产品优先级

**必须现在做**：R2 可信关系连续性，让搭子态第一次拥有可验证、可纠错的“认识我”。

**有真实用户后做**：记忆迁移、可靠待跟进、场景 Skills 目录、代理设置与诊断。

**明确不现在做**：沉浸式房间、自动情绪长文、持续后台 Agent、大型 Skills 市场。

这条顺序既保留 Leemo 的野心，也把下一次可验收进展压缩到一个真实核心旅程：**打开 momo → 看见它记得什么 → 发现错误 → 自己改正 → 下次对话确实生效。**
