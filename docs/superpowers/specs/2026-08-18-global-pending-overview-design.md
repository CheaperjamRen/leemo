# Leemo 全局“待完成事项”总览设计

> 日期：2026-08-18
> 状态：用户已确认的产品设计；工程实现与验收证据已落地。
> 权威范围：覆盖“开始”首页的全局待完成事项快照、手动梳理、可选每日自动梳理、来源证据、纠错和费用边界。
> 视觉稿：`docs/design-audition/visual-redesign/start-static-workspace-v2.png`

## 一、结论

“开始”首页原定的“继续工作”不再根据最近打开、最近编辑或模型猜测推断用户还想继续什么。它替换为一个**全局待完成事项快照**：

- 范围跨越全部本子、Todo、会话、Run、成果和已保存的项目概览；
- 用户点击“为我梳理待完成事项”或“重新梳理”时，才调用模型生成新的快照；
- 用户可以明确启用“每天指定时间后首次回到 Leemo 时自动梳理一次”；该自动化默认关闭；
- 未重新梳理时继续展示最近一次成功快照，不在打开页面、停留、悬停或普通数据变化时偷偷调用 API；
- 模型只负责归并、概括和排序，不能完成 Todo、修改便签、改变 Run 状态或把猜测写回事实对象。

这张看板是帮助用户找回全局位置的解释层，不是第二套任务数据库，也不是模型替用户作出的承诺清单。

## 二、用户心智

用户只需要理解三件事：

1. Todo、便签、会话、任务过程和成果仍然各自保留在原来的位置；
2. “待完成事项”把这些分散信息整理成一张可跳回来源的全局快照；
3. 只有用户手动刷新，或事先启用每日自动梳理，快照才会调用模型重新生成。

不向用户暴露候选收集器、source fingerprint、结构化输出 schema、embedding 或内部工作线 ID。

## 三、首页状态

### 3.1 尚未生成

首页 01 卡只显示：

- 标题“待完成事项”；
- 说明“从 Todo、近期会话和任务记录中梳理”；
- 主动作“为我梳理待完成事项”。

不得为了填满卡片生成示例事项、推荐内容或伪造优先级。

### 3.2 已有成功快照

首页最多预览前三项，每项显示：

- 事项标题；
- 所属本子 / 项目；
- 来源对象种类与数量；
- 可直接打开的来源；
- 最近成功更新时间。

卡片提供“重新梳理”和“查看完整看板”。首页预览不复制完整 Todo 列表，也不展示大段模型解释。

### 3.3 正在更新

旧快照继续可读，只在卡片标题区显示轻量进度“正在梳理…”。不得清空卡片、铺满骨架屏或阻塞“开始”的其他静态工具。

### 3.4 更新失败

保留最近一次成功快照，并显示一行低干扰状态：“本次更新失败，仍展示上次结果”。提供手动重试和折叠错误详情；失败不能变成空看板。

### 3.5 没有可整理内容

成功运行后若没有可靠候选，显示“暂时没有可确认的待完成事项”与更新时间。不得用普通闲聊、静默灵感或已完成事项补位。

## 四、候选来源

候选由本地确定性逻辑先收集，模型不能直接扫描并自行发现任意对象。

### 4.1 始终纳入

- 所有未完成 Todo；
- 当前仍在运行、等待用户、失败可重试或中断的 Run；
- 用户置顶或显式关联到 Todo / 项目 / 本子的工作对象；
- 已存在但尚未被用户标记结束的总览纠错记录。

### 4.2 有界纳入

- 最近 30 天内有用户指令、任务过程或成果变化的会话；
- 对应会话的最后一个可执行用户指令、最终回复、真实工具状态和成果引用；
- 最近 30 天内更新的本子 / 项目概览；
- 与上述对象存在稳定 ID 关系的成果和文件元数据。

普通闲聊、仅表达情绪的消息、无任务意图的问答、静默 Inbox 便签和正文全文默认不进入候选。模型输入优先使用已有摘要和有界事件，不发送整个文档库或全部历史会话。

## 五、事实层与解释层

### 5.1 本地事实包

每个候选先生成只包含真实 ID 的事实包：对象类型、当前状态、用户顺序、期限、所属本子、关联 Run、成果、最后用户指令和时间。敏感凭据、无关文件内容和不可验证的模型文本不得进入。

### 5.2 模型职责

模型可以：

- 把同一工作在 Todo、会话和成果中的分散信息归并为一个事项；
- 概括已经发生的进展和仍可能需要的动作；
- 在用户固定优先级之后做语义排序；
- 给出简短排序理由和来源引用。

模型不能：

- 创建、完成、删除或修改 Todo；
- 修改便签、文件、本子、Run 或成果；
- 按标题相似强行合并没有稳定关系的对象；
- 把“Agent 已交付”写成“用户已经完成”；
- 生成不存在的来源 ID、截止日期、进度或成果。

### 5.3 本地校验

模型输出必须经过结构化 schema 和来源 ID 校验。不存在的引用、重复项、越界对象和无证据字段全部拒绝；单项失败不能让整张旧快照消失。

## 六、排序与分组

首页和完整看板采用相同优先级：

1. 用户手动置顶或调整的优先级；
2. 等待用户回答、批准或提供材料；
3. 已逾期或今天到期的 Todo；
4. 失败可重试或中断的任务；
5. 近期有明确未完成指令且存在真实进展的工作；
6. 其他可靠候选。

模型只能在这些硬约束内细排。完整看板按本子 / 项目分组；没有归属的对象进入“未归组”，不能为了视觉整齐自动创建项目。

判断不清的候选不进入首页前三项，在完整看板底部折叠为“还有 N 项无法确认”，并附来源。它们不能冒充确定的待完成事项。

## 七、用户纠错

每项提供低干扰操作：

- **打开来源**：跳转到真实 Todo、会话、成果、本子或文件；
- **优先处理**：记录用户排序覆盖；
- **不再关注**：从未来总览候选中排除，保留原对象；
- **已经结束**：只结束总览事项，不自动完成关联 Todo。

用户纠错使用稳定对象 ID 持久化，下一次梳理必须先应用这些覆盖。若用户后来主动恢复关注，可以撤销排除。

## 八、快照与硬状态校正

首版只持久化最近一次成功快照、当前用户覆盖和必要来源指纹，不建设完整历史版本库。

在不调用模型的情况下，本地可以校正明确硬事实：

- 用户完成 Todo 后，相关条目不再作为未完成 Todo 展示；
- Run 从运行中变成失败、等待或已交付时，显示真实状态；
- 来源删除、归档或失效时显示来源状态，不跳转到错误页面；
- “Agent 已交付”不等于“用户已经结束”，除非用户明确纠正。

本地校正不重写模型摘要，也不重新排序整张看板；需要新的语义归并和排序时仍由用户手动刷新或已启用的自动化触发。

## 九、每日自动梳理

- 默认关闭；
- 用户选择本地时间；
- 在该时间之后，当天第一次进入 Leemo 前台时运行一次；应用从此前一直保持打开时，以第一次重新进入前台为准；
- 每个本地自然日最多自动运行一次；
- 设置中明确说明会调用当前模型并计入用户用量；
- 没有可用 Provider / 模型时不报全局错误、不清空旧看板，只在看板内给出中性提示；
- 自动运行失败时保留旧快照，允许手动重试；
- 用户关闭自动梳理后，不再因时间、启动或前台切换调用模型。

这属于用户事先明确启用的模型自动化，不构成“开始”页面默认主动说话。

## 十、完整看板

完整看板是全局视图，不局限于当前本子。它至少提供：

- 按本子 / 项目分组；
- 事项标题、进展摘要、建议下一步和来源；
- Todo、会话、Run、成果等来源入口；
- 用户排序、忽略、结束和恢复关注；
- 最近成功更新时间与本次模型用量入口。

完整看板不新建第二套 Todo，不要求用户维护 WorkThread，也不自动写回原对象。

## 十一、费用与隐私

- 手动梳理按钮必须明确是一次模型操作；
- 自动梳理必须由用户主动启用；
- 每次调用进入现有用量记录；
- 主进程继续持有凭据，快照和日志不得包含 API Key；
- 模型只接收完成本次归并所需的有界摘要和事实包；
- 普通浏览、编辑、搜索、整理、Todo 勾选和打开看板仍为零模型调用。

## 十二、首版非目标

- 不做实时 AI 推荐流；
- 不在每次打开“开始”时自动刷新；
- 不自动完成 Todo；
- 不自动创建项目、标签或工作线；
- 不保存无限历史快照；
- 不把静默灵感自动转换为候选；
- 不让模型替代原有 Todo、便签、会话和成果真源。

## 十三、验收旅程

1. 未生成快照时打开“开始”，模型调用为 0；
2. 点击“为我梳理待完成事项”后只调用一轮明确可见的模型任务，成功生成带真实来源的全局快照；
3. 不刷新时重启 Leemo，仍显示上次成功快照且模型调用为 0；
4. 模型返回不存在的对象 ID 时，本地拒绝该项且旧快照不丢；
5. 用户完成关联 Todo 后，本地展示不再把它称为未完成，且不调用模型；
6. 用户选择“已经结束”后，该总览项消失，但关联 Todo 状态不变；
7. 自动梳理默认关闭；启用 09:00 后，当天 09:00 后第一次进入前台只运行一次；
8. 自动梳理失败、断网或 Provider 不可用时保留旧快照并显示可重试状态；
9. 首页只预览三项，完整看板可按本子 / 项目查看全部可靠候选和来源；
10. 普通便签、Todo、文档和导航全过程仍可在无模型环境完整使用。
