## 一、全局架构总览

### 1.1 壳拓扑与视图路由

**不引路由库**。Electron 单窗单页、视图有限，视图状态收进一个新的轻量 `ui` store（§1.3.9）。目标拓扑：

```
App
└─ BridgeProvider（stores 装配，现有）
   └─ AppShell（新）——壳选择 + overlay 装配点，自身无视觉
      ├─ mode==='buddy'      → BuddyShell（现有，暖白缺省作用域）
      ├─ mode==='workbench'  → WorkbenchShell（S1 新建，根元素 data-shell="workbench"）
      ├─ ui.settingsOpen     → SettingsOverlay（S7；恒 data-shell="workbench"——设置是工具面，恒冷灰）
      ├─ ui.wizardOpen       → WizardOverlay（S8；恒暖白——第一印象=认识 momo）
      ├─ ui.searchOpen       → SearchPalette（S13；跟随当前壳基调）
      ├─ ui.wikiPopup        → WikiPopup（S10；跟随当前壳基调）
      └─ NotificationToasts（S15；跟随当前壳基调，常驻装配右下）
```

- **模式切换**：`settings.mode` 翻转 → 两壳交叉淡入 300ms（02§18），**store 不动、对话原地续**（activeId/timelines 全保留）。切换器 UI 归属各壳顶栏；快捷键 Ctrl+M 挂 AppShell 层（两壳生效）。
- **二级面归属**：设置=全屏 overlay（两壳可达，历史抽屉底部入口 + 工作台侧栏入口 + 快捷键无）；Skills/成果=**工作台内容区视图**（`ui.view: 'chat'|'skills'|'artifacts'`，经侧栏一级导航切换；buddy 态无直接入口——02§4 自己就是这么分配的，产物经轻产物卡"去工作台查看"引导，不违「全能力轻展示」）；搜索=悬浮窗两壳可用；向导=首启全屏（替代两壳渲染）+ 无 key 态各发送入口引导重开。

### 1.3 Store 契约总面（最高杠杆件——Opus 严格 TDD 的形状基准）

#### 1.3.0 四条全局纪律

1. **密钥纪律（硬）**：任何 store 字段、fixture、组件 props **不得出现 key 明文**。设置页/向导的 key 输入框是"一次性写入口"（提交即发主进程，Phase-1 走专用 invoke；fixture 期直接丢弃并置 `configured:true`），渲染层永不留存。store 只存 `configured: boolean` 类事实。
2. **端口纪律（现有铁律延续）**：新 store 一律经 `BridgeClient` 端口 invoke/subscribe；新组件一律经 context hooks 读 store（guard.test 自动覆盖新文件）。
3. **订阅生命周期（Phase-1 gate 顺带偿还）**：新 store 的 `client.subscribe` 统一收敛到**一个装配函数** `wireBridgeSubscriptions(client, stores): () => void`（返回聚合 unsubscribe），由 BridgeProvider 持有并在卸载时调用——不再把订阅散在各 store 工厂里丢 unsubscribe（修复 fe-slice1 gate①的结构性根源；conversations.ts 重构时一并迁入）。
4. **reducer 纯函数范式**：一切事件→状态迁移写成可单测纯函数（对齐 `applyEvent` 风格）；store 工厂只做装配。

#### 1.3.1 `conversations.ts` —— 重构（单对话 → 多对话注册表）⚠risk 卡（动现有绿测试）

02 附 A 的 `runs.toolCalls/todos/subagents` 职责**已被 TimelineItem 判别联合吸收**（tool/plan/activity/thinking/compact/usage/result 全在时间线里，slice-2 落地并 K3 穿衣完毕）——**不设独立 runs store**，避免双写同步 bug。"runs"残余的跨对话横切状态（哪个对话在跑、哪个待审批）收进本 store 的 per-conversation 字段；圆环数据独立成 §1.3.4。

```ts
export interface ConversationMeta {
  id: string;
  title: string;                     // 自动标题=首条用户消息截 24 字；空对话="新对话"
  titleManuallyUpdated: boolean;     // 08§五 手改保护位：true 后自动标题不再覆盖
  bookId: string | null;             // null = 放养
  source: "buddy" | "workbench";     // 创建时所在壳（08§四）
  providerId: string;
  modelId: string;
  createdAt: number;                 // epoch ms
  lastActivityAt: number;            // 排序/分组键
  unread: boolean;                   // 侧栏徽标●：非激活期间 run.finished → true；switchActive → false
}

export interface ConversationsState {
  byId: Record<string, ConversationMeta>;
  order: string[];                   // 新→旧（lastActivityAt 降序维护）
  activeId: string | null;           // null = 首启空态（buddy 落地页）
  openTabs: string[];                // 工作台标签条 ≤5；buddy 态恒 ≤1（点历史=替换而非加标签）
  timelines: Record<string, TimelineItem[]>;   // per-conversation applyEvent 输出
  runIds: Record<string, string | null>;       // per-conversation activeRunId（null=空闲）

  createConversation(opts: { source: "buddy" | "workbench"; bookId?: string | null }): Promise<string>;
  send(conversationId: string, text: string): Promise<void>;      // 起新 runId、推用户消息、invoke bridge:send
  interrupt(conversationId: string): Promise<void>;
  switchActive(conversationId: string): void;                     // 清 unread；buddy 抽屉与 workbench 侧栏共用
  openTab(conversationId: string): void;                          // >5 时拒绝并提示关一个（02§五"超出提示关闭"）
  closeTab(conversationId: string): void;                         // 关激活标签→激活左邻；关最后一个→activeId=null 空态
  renameTitle(conversationId: string, title: string): void;       // 置 titleManuallyUpdated=true
  assignToBook(conversationId: string, bookId: string | null): void;
  setModelForConversation(conversationId: string, modelId: string): Promise<void>; // 同 Provider 内换模型（见下）
}
```

- **跨 Provider 换模型裁定**：冻结契约 `SetModelRequest = {conversationId, modelId}` 无 providerId；且 per-provider `CLAUDE_CONFIG_DIR` 隔离使跨 provider resume 不可行。06§3.4"选择即写入 conversation.{providerId,modelId}"与契约冲突，按权威链 09 胜出——**中途换模型=同 Provider 内**；模型面板里其它 Provider 的模型显示可选但点击=引导「用该模型开新对话」（S6①折叠状态条）。此为架构事实裁定，不进 ⚠。
- **自动标题**：send() 时若 `title==="新对话" && !titleManuallyUpdated` → 以本条消息截 24 字设 title。
- 现有单对话版的 `send/interrupt/applyEvent 装配`语义逐字保留，只是从顶层字段搬进 map；现有组件改动=选择器收窄（`s.messages` → `s.timelines[s.activeId] ?? []`），组件 JSX 零改。

#### 1.3.2 `approvals.ts` —— 新建（回投通道数据面）⚠risk 卡

```ts
export type PendingInteraction =
  | { kind: "approval"; id: string; conversationId: string; runId: string;
      toolName: string; inputSummary: string; risk: RiskLevel; receivedAt: number }
  | { kind: "question"; id: string; conversationId: string; runId: string;
      questions: AskUserQuestion[]; receivedAt: number };

export type ResolvedInteraction =
  | { kind: "approval"; id: string; runId: string; toolName: string; inputSummary: string;
      risk: RiskLevel; outcome: ApprovalTier | "cancelled" }
  | { kind: "question"; id: string; runId: string; questions: AskUserQuestion[];
      items: AskUserAnswerItem[] | null /* null=cancelled */ };

export interface ApprovalsState {
  pendingByConversation: Record<string, PendingInteraction | null>; // SDK 串行阻塞 ⇒ 每对话至多一张挂起
  resolvedByRun: Record<string, ResolvedInteraction[]>;             // 已答卡原位灰化渲染的数据源
  whitelist: WhitelistEntry[];                                      // 裁决③：bridge:listWhitelist 镜像（设置页权限分区）
  decide(id: string, decision: ApprovalTier, message?: string): Promise<void>; // → bridge:approvalDecision
  answer(id: string, items: AskUserAnswerItem[]): Promise<void>;              // → bridge:askUserAnswer
  cancelForConversation(conversationId: string): void; // run.finished(interrupted|error) 时挂起卡转 cancelled
  refreshWhitelist(): Promise<void>;                                // → bridge:listWhitelist
  revokeWhitelistEntry(entry: { toolName: string; risk: RiskLevel }): Promise<void>; // → bridge:revokeWhitelist 后 refresh
}
```

- 事件源：`subscribe("bridge:approvalRequest")` / `subscribe("bridge:askUser")`。归属直接读 `payload.conversationId`（裁决①字段）；`runId` 本地反查 `conversations.runIds[payload.conversationId]`（§1.4）。
- `decide/answer` 落定后：挂起卡搬进 `resolvedByRun[runId]`（含 outcome），挂起位清 null——**已答卡不消失**（审计痕迹 + 防布局跳动，S2②/S3② 有已答态视觉）。
- run.finished 到达时（conversations 的订阅回调里顺带调 `cancelForConversation`）：若仍有挂起卡（interrupt/错误把 run 终结了），转 `outcome:"cancelled"`。

### 1.4 事件路由规则（7/23 裁决①落地后的最终形态——按 conversationId 精确路由）

三条推送通道经裁决①补齐归属字段（`bridge:event` 信封 `{conversationId, event}`；`ApprovalRequest`/`AskUserPayload` 带必填 `conversationId`）。路由规则简单且无歧义：

- `wireBridgeSubscriptions` 的 `bridge:event` 回调**解信封**，把 `event` 折入 `timelines[envelope.conversationId]`（`applyEvent` 签名不变——信封在订阅层解掉，reducer 只见裸 `LeemoEvent`）；`runId` 参数取 `runIds[envelope.conversationId]`（渲染层自己发号并维护的现有机制，Bridge 不产 runId——裁决①的精度修正）。
- `bridge:approvalRequest`/`bridge:askUser` 回调直接读 `payload.conversationId` 归属，同法反查 runId。
- **多对话并发直播成立**：对话 A 后台跑、用户在对话 B 里聊，两边时间线/徽标/通知都精确更新——这是用户点名的核心能力（"多任务/多会话后台并行不乱，对齐成熟 Agent"）。侧栏「进行中●/待审批⚠/后台完成✓」徽标（S16）对非激活对话**完全可靠**，无降级语义。
- 模式切换（buddy⇄工作台）不换 activeId，天然无路由问题（02§2.1 场景成立，与裁决前一致）。
- wiki 影子对话有自己的 conversationId，与主对话并发流式**互不干扰**——S10 原设计的"流式互斥软拦"已随裁决①**删除**（不再需要）。
- fixture 侧同步升级：`FixtureBridgeClient.emit` 一并发信封（fixture 里 conversationId 即当次 send 的目标 id），S 面组件与 store 在 fixture/真 IPC 两态下行为一致。

### 1.5 回投通道统一时序（审批条/问询卡共用骨架——最易出 bug 处，逐拍写死）

```
[SDK 侧]  模型要用工具 → canUseTool 阻塞 / ask_user 工具阻塞（waiters Map）
[Bridge]  推 bridge:approvalRequest{id,conversationId,toolName,inputSummary,risk} / bridge:askUser{id,conversationId,questions}
[store]   approvals 订阅回调：cid=payload.conversationId（裁决①字段），runId=runIds[cid] 本地反查（§1.4）
          → pendingByConversation[cid] = 卡
[渲染]    TurnBlock（该 runId 的回合块）在其节点序列**末尾**追加 ApprovalBar/AskUserCard
          —— 位置论证：SDK 在 resolve 前不推进该 run 的任何新事件，挂起卡必然是回合尾项；
             不猜 toolUseId 拼接位置（契约没给），不进 ProcessFold（待办卡折进折叠区=灾难）
          ProcessFold 保持展开（active 判定=runIds 非 null，阻塞期间恒成立，现有逻辑零改）
[用户]    点档位/选项 → store.decide(id,tier) / store.answer(id,items)
[store]   invoke bridge:approvalDecision/bridge:askUserAnswer；挂起卡→resolvedByRun[runId]（含 outcome）
          **乐观迁移**：invoke 前先迁（点击即灰化防双击）；invoke reject → 回滚为 pending + toast 错误
[Bridge]  broker/waiters resolve → SDK 续跑 → 后续事件恢复流入（工具执行、text.delta…）
[渲染]    已答卡原位保留（灰化缩小态，S2②/S3②）；新事件继续追加在其后
```

**中断/异常路径**（必须与主路径同权重实现）：
- 用户点停止 → `interrupt` → SDK abort → `run.finished(subtype:"interrupted")` → conversations 订阅回调调 `approvals.cancelForConversation` → 挂起卡转「已取消」已答态（不可再点）。
- run error 同路径（subtype/error 事件）。
- 答卡与停止赛跑：decide/answer 时挂起位已是 null（被 cancel 抢先）→ no-op 返回（不抛、不重复 invoke）。
- 多问并发：契约允许（waiters 隔离），但 SDK 工具串行使实际同刻至多一张；store 以「每对话一张挂起位」建模，若真收到第二张（防御）→ 顶替旧卡并把旧卡记为 cancelled（日志留痕）。

## 二、裁决记录（用户 2026-07-23 五项已决——Bridge/Opus 执行时对照本节最终形状）

**①A1（事件归属字段）—— 做，多对话后台并行是核心能力，对齐成熟 Agent（用户原话）**

最终字段面（写这里，Bridge 卡照此实现，不再讨论）：
- `bridge:event` 的 payload **从 `LeemoEvent` 升级为信封** `{ conversationId: string; event: LeemoEvent }`（`BridgeEventMap["bridge:event"]` 类型改写）。选信封而非给 11 个 variant 各加字段：conversationId 是**路由用的 IPC 信封字段**,不是事件语义的一部分,散加进每个 variant 容易在未来新增第 12 个 variant 时漏加;信封只有一处。
- `ApprovalRequest` 加 `conversationId: string`（必填）。
- `AskUserPayload` 加 `conversationId: string`（必填）。
- **`runId` 明确不需要 Bridge 提供**——重要澄清（设计过程中核实出的事实）：`runId` 是**渲染层自己发号的概念**（`conversations.ts` 现有 `runSeq` 自增），Bridge/`events.ts`/`interact.ts` 全链路根本没有"runId"这个东西，SDK 每次 `query()`/`canUseTool` 也不携带它。前端拿到 `conversationId` 后，用**已有机制** `conversations.runIds[conversationId]`（本对话当前活跃的 run）本地反查即可定位回合块——同一对话同一时刻只有一个活跃 run，反查恒对。**只加 conversationId，不要求 Bridge 生产它给不出的 runId 字段**，这是本次裁决落地时对原始建议的一处精度修正。
- 这是本次唯一的**契约形状级改动**（非纯加可选字段）——09 文档记一行"v1.0→v1.1：`bridge:event` 信封化，为多对话路由"，不必整体重开 v2.0 流程（无 Phase-1 消费方在线，评估为可 in-place 修订）。
- **架构收益（直接解锁,下面几处设计已按此收紧）**：§1.4 事件路由规则从"最近 send() 猜测"的临时/易错启发式，**升级为按 conversationId 精确路由**——真正支持"对话 A 在后台跑着，用户在对话 B 里聊天，两边状态都精确更新"，侧栏「后台完成✓」徽标、wiki 弹窗与主对话并发、跨会话通知全部不再需要降级说明。

**①布局与位置**（K3 workbench 稿 §5 原样，两壳通用密度——02§4.3 明写"审批条/问询卡：与工作台同组件的轻样式变体"，即**同一组件**接受一个 `density?: 'default'|'buddy'` 视觉调整 prop，非两套组件）

  <span class="grid h-[30px] w-[30px] place-items-center rounded-[8px] border bg-white/80"><ShieldIcon/></span>

    <p class="mono mt-[3px] w-fit truncate rounded-[5px] border bg-white/80 px-1.5 py-px text-[11.5px]">{inputSummary}</p>
    {dangerLocked && <p class="mt-1 text-[11px] text-danger">危险操作，每次都会问你（可在设置→权限里调整）</p>}
  </div>
  <div class="ml-auto flex shrink-0 items-center gap-2">
    <button>拒绝</button>
    {!dangerLocked && <button>本对话总是允许</button>}
    {!dangerLocked && <button>永久允许</button>}
    <button class="bg-ink text-white">允许一次</button>
  </div>

- `dangerLocked = risk==='dangerous' && !settings.dangerousCommandCaching`。dangerLocked 时只给「允许一次」；开关开启后 dangerous 可给「本对话允许」，但**任何 dangerous 与任何 Shell 命令都不显示「永久允许」**。Shell 的本对话缓存只覆盖完全相同命令，审批卡必须明写「仅这条命令；不会跨对话永久放行」。普通非 Shell 工具的本对话/永久按钮则明写「此类操作」，避免具体输入与真实授权范围不一致。
- `verbOf(toolName)`：小映射表 `{Write:"写入文件", Edit:"编辑文件", Bash:"执行命令", NotebookEdit:"编辑笔记本"}`，未知工具名 → `"使用 {toolName}"`。
- **路径角标降级说明（如实记录，非裁决项）**：02§7.6 原文"cwd 外绝对路径写入时条上加⚠工作区外角标"在当前契约下**做不到**——`ApprovalRequest.inputSummary` 是 Bridge 拼好的自由格式字符串（非结构化路径 + 无 cwd 字段），前端没有可靠判据，不伪造。真正的路径审计已在**执行后**的 `MessageFooter`（`pathAudit`，Bridge 端 `existsSync`+cwd 比对真实计算）生效——用户会在回合尾部看到"⚠ 声称写到工作区外"。审批阶段只能如实展示 inputSummary 原文；Phase-1 若要审批前置角标，需给 `ApprovalRequest` 再加结构化 path/cwd 字段（本次裁决①未纳入此项，留 backlog，不阻塞）。

**②状态机**：`pending`（如上，可交互）→ `resolved-{tier}`（灰化态：整条透明度 0.55、按钮全部消失、右侧追加一枚小标签"已允许一次"/"本对话内总允许"/"已拒绝"/"已永久允许"）→ `cancelled`（run 被中断/出错时挂起卡的终态，标签"已取消"）。乐观迁移：点击按钮→**立即**转 resolved（灰化）+ 禁用整卡指针事件，`decide()` 的 Promise reject 时**回滚**为 pending 并 toast「没送出去，再点一次？」。

**③store 契约**：`approvals.pendingByConversation[activeId]`（渲染源）、`approvals.resolvedByRun[runId]`（灰化态源，TurnBlock 按 runId 取本回合已答历史，可能 >1 张——同回合多次工具调用都要审批时顺序追加）、`decide(id, tier, message?)`。危险态判定读 `settings.dangerousCommandCaching`。

**④交互时序**：见 §1.5 总时序图，本面无额外分支。**渲染定位**：TurnBlock 对 `runId===g.runId` 的块，在其节点序列末尾（`MessageFooter` 之前，因为 result 尚未到达——运行被阻塞）追加 `approvals.pendingByConversation[cid]?.runId===g.runId ? <ApprovalBar/> : null`，随后追加 `resolvedByRun[g.runId].filter(kind==='approval')` 的历史灰卡（按 receivedAt 序）。**不进 ProcessFold**——批准前用户必须一眼看见,折叠=灾难性可用性 bug。

**⑤双基调映射**：琥珀色系两壳同值（K3 两稿本就同值），无需重赋；`--leemo-danger-soft`/`--leemo-danger-line` 为**新增 token**（`:root` 值 `rgba(222,82,76,.08)` / `rgba(222,82,76,.35)` 估算，两壳同值——危险色不该随基调变暖变冷,危险感必须恒定）。

**⑥复用边界**：全新组件 `ApprovalBar.tsx`。图标复用 K3 shield symbol（转 inline SVG，仿 ToolCard 现有 SVG 写法）。
